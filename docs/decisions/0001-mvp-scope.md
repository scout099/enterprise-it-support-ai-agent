# ADR-0001：MVP 范围与基础架构选择

- **状态**：Accepted
- **日期**：2026-07-19
- **决策范围**：Enterprise IT Support AI Agent 个人作品集 MVP

## 1. 背景

项目最终可以扩展为大型企业内部 IT 支持平台，但当前目标是完成一个个人可以构建、测试、演示并在面试中清楚解释的 MVP。MVP 必须覆盖企业知识导入、pgvector 检索、带引用 RAG、三类请求诊断、受控只读 Mock 工具、本地工单、审计、评估和简单 Web UI。

项目维护者仍在学习 Python、FastAPI、数据库、RAG、LangGraph 和 Agent 工程。架构既要符合真实 AI 应用的安全与可观察性原则，也要控制同时学习和调试的变量数量。

## 2. 决策

我们决定：

1. MVP 使用模块化单体；
2. 第一版不拆分微服务；
3. 外部企业系统统一使用只读 Mock Adapter；
4. PostgreSQL 作为业务数据库，并使用 pgvector 保存和检索向量；
5. 先完成可评估的 RAG，再引入 LangGraph 编排三类诊断工作流。

## 3. 为什么选择模块化单体

模块化单体让 FastAPI、Agent Runtime、Knowledge、Tools、Policy、Ticketing 和 Evaluation 在一个代码库和一个应用部署中协作，同时保持按业务能力划分的模块和单向依赖。

选择它的原因：

- **降低运行复杂度**：本地只需运行应用与 PostgreSQL/pgvector；
- **保留事务一致性**：Agent Run、工具审计和本地工单可以使用清晰的本地事务规则；
- **提高开发反馈速度**：接口变更、迁移和集成测试都在一个仓库内完成；
- **便于学习和讲解**：可以集中理解请求如何穿过各模块，而不是先处理网络通信和部署问题；
- **不牺牲模块质量**：模块仍拥有明确 interface、内部实现和测试面，禁止跨模块随意访问数据表或 Adapter。

模块化单体不是“把所有逻辑写在一个文件”。它是单一部署形态下的模块化设计。

## 4. 为什么第一版不使用微服务

微服务解决的是独立扩缩容、团队自治、故障隔离和独立发布等组织与运行问题。当前 MVP 没有这些已被证明的需求，却会立即增加：

- 网络调用、超时、重试和兼容性管理；
- 分布式数据一致性和跨进程追踪；
- 多个部署单元的配置、测试和本地启动成本；
- 对学习重点的干扰，使时间从 RAG、Agent 安全和评估转向基础设施。

因此第一版不提前支付这些成本。未来只有在出现清晰证据时才考虑拆分，例如知识导入需要独立扩缩容、评估任务影响在线请求，或者不同团队需要独立发布。即使发生拆分，也应沿现有模块 interface 和数据所有权进行，而不是按技术层随意拆分。

## 5. 为什么外部企业系统使用 Mock Adapter

真实的 ServiceNow、Microsoft 365、Active Directory、Entra ID 和 Intune 接入需要企业租户、敏感凭证、管理员授权和安全审查。个人作品集不应依赖这些条件，也不应为了演示申请或保存高权限凭证。

只读 Mock Adapter 可以验证真正重要的 Agent 工程行为：

- Agent 能否选择正确的已注册工具；
- 参数是否通过 Schema 校验；
- Policy 是否正确允许或拒绝；
- 工具失败是否安全处理；
- 每次尝试是否产生审计记录；
- 诊断是否正确使用工具结果，而不是编造状态。

Mock Adapter 必须返回现实、结构化且可配置的成功、失败和边界场景，不能只返回永远成功的固定字符串。它们是 MVP 演示中的外部系统替身，不是假装测试通过的无意义 Mock。

未来真实 Adapter 只能接入 Tool Gateway 和 Tool Registry 已定义的 seam。Agent Runtime 不感知具体供应商 SDK，也不能直接持有企业凭证。

## 6. 为什么选择 PostgreSQL + pgvector

MVP 同时需要保存关系数据和向量数据：

- 文档、版本、Chunk 和来源；
- 会话、Agent Run 和 Step；
- 工具调用与 Policy 审计；
- 本地工单；
- 评估数据集和结果；
- Chunk Embedding 与相似度索引。

PostgreSQL 适合前述事务和关系查询，pgvector 让同一数据库也能完成 MVP 所需的向量相似度检索。这样可以：

- 减少一种独立数据基础设施；
- 在文档状态、来源元数据和向量查询之间使用一致过滤；
- 让迁移、备份、本地开发和集成测试保持简单；
- 为未来的全文检索、元数据过滤和混合检索保留空间；
- 用一个完整数据模型展示 RAG 与业务数据如何关联。

代价是超大规模向量检索的专用能力可能不如独立向量平台，但 MVP 没有该规模需求。未来是否更换检索存储，应由语料规模、延迟、召回率和运维数据决定，Knowledge Retrieval 的 interface 将隔离这一变化。

## 7. 为什么先完成 RAG，再引入 LangGraph

诊断 Agent 依赖可信的知识检索。如果文档解析、Chunk、Embedding、召回、引用或无证据拒答尚不稳定，过早加入状态图会让错误来源混在一起：无法判断失败来自检索、模型、状态转换还是工具选择。

先完成 RAG 可以建立：

- 可重复的文档导入和检索数据；
- 明确的证据与 citation ID；
- Model Gateway 和结构化输出；
- 无证据安全拒答；
- Retrieval 与 Generation 的独立评估基线。

在这些能力稳定后，LangGraph 只负责它真正有价值的部分：显式状态、三类诊断流程、澄清、步骤记录、工具节点、结束条件和错误恢复。这样每一层都能单独测试和解释，也避免把简单 RAG 误建成复杂 Agent。

## 8. 后果

### 8.1 正面后果

- MVP 运行和调试路径短；
- 业务模块、Policy 和工具治理从第一版就清晰存在；
- RAG、Agent 和评估可以按阶段建立可测基线；
- 作品集能展示完整工程闭环，而不是只有聊天界面；
- 未来真实模型、工具或检索实现可以在 seam 后替换。

### 8.2 负面后果与接受方式

- 单个应用进程的能力有限：MVP 接受该限制，并避免宣称生产级规模；
- Mock Adapter 不能证明真实企业接口兼容性：文档和 UI 必须明确标记 Mock；
- PostgreSQL 同时承担多种数据负载：通过模块数据所有权、索引和评估观察其是否成为真实瓶颈；
- LangGraph 引入较晚：前期使用普通应用流程完成 RAG，这是有意的分层学习顺序，不是遗漏 Agent 能力。

## 9. 被拒绝的方案

### 9.1 从第一天拆分多个独立部署单元

拒绝原因：没有独立团队、扩缩容或发布需求，增加的分布式复杂度无法提升 MVP 价值。

### 9.2 第一版连接真实企业系统

拒绝原因：需要真实租户和高权限凭证，安全风险高、不可复现，也不利于公开作品集演示。

### 9.3 同时使用关系数据库和独立向量存储

拒绝原因：当前语料规模不需要额外系统，跨存储一致性和本地运行成本高于收益。

### 9.4 先实现自由循环 Agent，再补知识和评估

拒绝原因：缺乏可靠证据、显式约束和质量基线，难以诊断幻觉、错误工具选择和工作流失败。

## 10. 复审触发条件

出现以下可测证据时，可以新建 ADR 复审本决策：

- 单个模块的资源或发布周期明显不同，并持续影响其他模块；
- pgvector 在代表性语料和查询上无法达到已定义的召回或延迟目标；
- 需要接入已授权的真实企业测试租户；
- 在线请求与导入或评估任务之间出现无法通过简单隔离解决的资源竞争；
- 产品范围从个人作品集演示变为有明确安全、容量和可用性要求的真实企业部署。

在触发条件出现前，优先改进现有模块的深度、interface 和测试，而不是增加部署复杂度。
