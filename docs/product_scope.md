# Enterprise IT Support AI Agent：MVP 产品范围

## 1. 文档目的

本文档定义个人作品集版本的最小可行产品（MVP）范围。后续阶段以本文档判断某项需求是否应进入当前版本，避免把“最终可扩展的平台愿景”误当作第一版交付范围。

## 2. 产品定位

Enterprise IT Support AI Agent 是面向企业内部员工的 IT 支持应用。它以企业知识库为事实来源，识别常见 IT 请求，执行可解释的基础诊断，通过受控的只读 Mock 工具补充状态信息，在必要时创建本地 IT 工单，并保存引用、Agent 执行轨迹、工具审计记录和评估结果。

MVP 的价值不是代替整个 IT 服务台，而是验证一条可信、可追踪的闭环：

> 员工提出问题 → 系统识别请求 → 检索授权知识 → 执行基础诊断 → 必要时调用受控工具 → 回答或创建工单 → 记录并评估全过程。

## 3. 用户角色

| 用户角色 | 主要目标 | MVP 中的权限与能力 |
| --- | --- | --- |
| 企业员工 | 快速解决 VPN、Outlook、账号问题 | 提问、补充诊断信息、查看引用、查看工具结果、创建工单、提交反馈 |
| IT 支持人员 | 获得结构化问题上下文，减少重复排查 | 查看本地工单、诊断摘要、引用、Agent 执行轨迹和只读工具结果 |
| 知识库维护者 | 让系统使用最新且可追溯的内部资料 | 导入 Markdown、TXT、PDF 文档，查看导入结果和文档元数据 |
| 项目维护者 | 验证系统质量并定位失败原因 | 管理本地评估数据集，运行基础评估，查看检索、回答、分类和工具指标 |

MVP 不实现完整的企业组织管理。演示环境使用预置的本地用户身份和权限，Policy 模块仍必须参与所有工具调用，为未来接入企业身份系统保留明确的 seam。

## 4. 核心使用场景

### 4.1 导入企业 IT 知识

知识库维护者导入 Markdown、TXT 或 PDF 文档。系统解析文本、保留来源和文档元数据、切分内容、生成向量并写入 PostgreSQL/pgvector。失败的文档必须返回可理解的失败原因，不能静默忽略。

### 4.2 基于知识库回答问题

员工询问企业 IT 使用方法，例如“Mac 如何配置公司 VPN”。系统检索相关内容，生成只基于检索证据的回答，并提供文档名称、片段或页码等来源引用。证据不足时应明确说明无法确认，而不是依赖模型常识补全企业规则。

### 4.3 识别 IT 请求类型

系统把请求识别为以下四种结果之一：

- VPN；
- Outlook；
- 账号；
- Other / 无法可靠识别。

分类结果必须包含置信度或可解释理由。低置信度请求不得被强行路由到错误工作流。

### 4.4 执行基础诊断工作流

对于 VPN、Outlook、账号问题，系统使用对应的基础工作流：

1. 收集该类问题所需的最少信息；
2. 查询知识库；
3. 在允许时调用只读 Mock 工具；
4. 汇总已验证事实、建议步骤和仍未知的信息；
5. 判断是给出解决建议，还是建议创建工单。

工作流应可追踪、可恢复、可测试，不能只存在于一段不可观察的 Prompt 中。

### 4.5 调用受控只读工具

系统可通过 Mock Adapter 查询演示数据，例如：

- VPN 服务状态；
- Outlook 服务状态；
- 本地演示账号是否锁定。

每次调用都必须经过 Tool Registry、输入 Schema 校验和 Policy 权限检查，并写入审计记录。LLM 只能提出结构化的工具调用请求，不能直接执行 Shell、Python、SQL 或系统命令。

### 4.6 创建本地 IT 工单

当问题无法解决或用户主动要求升级时，系统在本地 PostgreSQL 中创建 IT 工单。工单包含用户问题、请求类型、诊断摘要、已尝试步骤、相关引用、工具结果和关联的 Agent Run ID。

### 4.7 评估 Agent 表现

项目维护者可以使用版本化的本地数据集运行基础评估，至少覆盖：

- 检索是否找到正确证据；
- 回答是否有依据且引用正确；
- 请求分类是否正确；
- 工具是否选对且参数有效；
- 诊断工作流是否到达预期结果。

## 5. MVP 功能范围

| 能力 | MVP 交付内容 |
| --- | --- |
| 文档导入 | 本地上传 Markdown、TXT、PDF；解析状态和错误可见 |
| 知识存储 | PostgreSQL 保存文档、版本、Chunk、引用元数据；pgvector 保存向量 |
| 检索 | 基于 PostgreSQL 的向量检索，并保留升级到混合检索和重排的模块内部空间 |
| RAG 问答 | 基于检索证据回答；带来源引用；证据不足时拒绝猜测 |
| 请求分类 | VPN、Outlook、账号、Other |
| 诊断 | 三类基础工作流，支持澄清、检索、只读工具和升级判断 |
| 工具 | Tool Registry、Schema 校验、Policy、只读 Mock Adapter |
| 工单 | 在本地数据库创建和查看工单 |
| 审计 | 保存工具请求、授权决策、参数摘要、结果、时间和关联 Run ID |
| Agent 轨迹 | 保存一次请求及其步骤、状态、引用、模型和 Prompt 版本 |
| 评估 | 本地数据集、基础指标、可重复运行的评估报告 |
| Web UI | 简单的提问、引用展示、诊断进度、工单结果和文档导入界面 |
| 运行方式 | 使用 Docker Compose 启动应用和 PostgreSQL/pgvector |

## 6. 明确不做的功能

以下内容属于未来企业版本，不进入个人作品集 MVP：

- 连接真实 ServiceNow、Microsoft 365、Active Directory、Entra ID、Intune 等企业账户；
- 修改账号、重置密码、安装软件、修改权限等有副作用的远程操作；
- 完整的企业 SSO、组织同步、细粒度文档 ACL 和多租户隔离；
- 自动处理全公司重大事件、值班调度、SLA 计费或复杂审批链；
- 邮件、Teams、Slack 等多渠道接入；
- 语音、图片故障识别和远程桌面控制；
- 自动抓取任意网站或持续同步外部知识源；
- 任意代码、命令、SQL 或脚本执行能力；
- 为未来规模预先拆分独立部署单元或引入复杂分布式基础设施；
- 生产级高可用、跨地域容灾和海量并发优化。

未来扩展必须保持相同的安全原则：LLM 提出建议，确定性代码负责校验、授权和执行。

## 7. 项目成功标准

### 7.1 功能完成标准

- 三种文档格式都能通过公开的导入流程进入知识库，并保留可追溯来源；
- 对知识库有支持的问题，回答展示至少一个可验证引用；证据不足时明确拒绝猜测；
- VPN、Outlook、账号和 Other 请求均能进入正确路由；
- 三类基础诊断流程都有成功、信息不足和升级工单路径；
- 所有工具调用都经过 Registry、Schema 校验和 Policy，且无绕过路径；
- 每次工具调用尝试都产生审计记录，包括被拒绝或失败的调用；
- 用户可以从一次未解决的诊断创建本地工单；
- Agent Run 能关联消息、步骤、引用、工具调用、工单和评估结果；
- 全新环境可以按照 README 使用 Docker Compose 启动并完成演示流程。

### 7.2 质量基线

在项目自带、版本化且人工核验的评估集上，MVP 目标为：

| 指标 | MVP 目标 |
| --- | --- |
| 文档导入集成测试 | Markdown、TXT、PDF 全部通过 |
| Retrieval Hit@5 | 不低于 85% |
| 有依据回答的引用覆盖率 | 100% |
| 无证据场景的安全拒答率 | 100% |
| 四分类 Macro F1 | 不低于 0.90 |
| 预定义诊断场景完成率 | 不低于 90% |
| 工具调用审计覆盖率 | 100% |
| 核心单元与关键集成测试 | 全部通过，不允许跳过 |

这些数值用于建立可讨论的工程基线，不代表通用行业标准。评估集必须同时包含正常案例、信息不足案例、越权工具请求和无知识证据案例，避免只测试“容易成功”的路径。

### 7.3 作品集与面试成功标准

- 能用一张架构图解释请求如何经过 FastAPI、Agent、RAG、Policy、Tool 和 Evaluation；
- 能解释为什么 LLM 不拥有最终授权权力；
- 能展示至少一条完整轨迹：问题、分类、检索、引用、工具调用、审计、回答或工单；
- 能用评估结果说明一次 Prompt、检索或工作流变更是否真正改进系统；
- 能明确区分 MVP 的工程取舍与未来企业平台可能采用的扩展方案。
